# Milton auth

Dedicated Node 26 auth service for `https://auth.meetmilton.com`. Better Auth owns passwords, native Google/GitHub OAuth, email verification/recovery, cookies, OAuth/OIDC, signing and refresh. Auth never serves writing, billing, app sessions or MCP tools. `api.meetmilton.com` is unused.

## Development and checks

From the repository root, using the existing Bun toolchain:

```sh
bun --no-env-file install --frozen-lockfile
bun --no-env-file run --cwd apps/auth check-types
bun --no-env-file test apps/auth/test
bun --no-env-file run --cwd apps/auth build
node --experimental-strip-types apps/auth/scripts/integration.ts
```

The integration command requires Node 26 and local PostgreSQL 18 binaries (`PG_BIN`, default `/opt/homebrew/opt/postgresql@18/bin`). It checks port 55543 is free, creates a uniquely named disposable directory/cluster/database, uses separate SCRAM runtime logins, runs actual product modules/native handlers and reviewed migrations, checks ports 19911/19912 before owned HTTPS and standalone bundle listeners, and stops/removes only that owned cluster/listeners in `finally`. It loads no dotenv file, reads no live configuration and refuses external network except explicitly mocked mail/admission/social boundaries. Run with a clean environment. Do not point it at another database. Native rate windows are owner-cleared between independent flow groups; production limits remain enabled. Temporary native read wrappers in the script pause actual library reads; there are no request/environment fault controls in product code.

The production entry point is `dist/cloud-run.js`. The build includes local theme CSS, fonts, favicon, native library dependencies and the local common-password hash list. It bundles for Node, not Bun. No runtime schema migration, provisioning, runtime dependency download or third-party asset fetch occurs.

## Fixed protocol contract

Issuer `https://auth.meetmilton.com/api/auth`.

| Surface               | Issuer-relative path                                 |
| --------------------- | ---------------------------------------------------- |
| OIDC discovery        | `/.well-known/openid-configuration`                  |
| OAuth discovery       | `/.well-known/oauth-authorization-server`            |
| JWKS                  | `/jwks`                                              |
| Authorize             | `/oauth2/authorize`                                  |
| Token / refresh       | `/oauth2/token`                                      |
| UserInfo              | `/oauth2/userinfo`                                   |
| End session / confirm | `/oauth2/end-session`, `/oauth2/end-session/confirm` |
| Public DCR            | `/oauth2/register`                                   |

The one first-party app client uses confidential code/S256, `client_secret_post`, `openid profile email`, no resource and no offline grant. Exact callback: `https://app.meetmilton.com/auth/callback`; logout return: `https://app.meetmilton.com/auth/logged-out`. App sessions expire no later than the one-hour opaque access token. Renewal is a new state/nonce/PKCE code flow through the auth SSO session, never a restamp of old authority. Native SSO lasts seven days with database-backed rolling renewal; sensitive operations require proof within five minutes.

AIs get only `https://mcp.meetmilton.com/mcp`. Access tokens are native EdDSA `at+jwt`, one-hour expiry; native rotating refresh tokens have a 30-day reference ceiling and zero replay grace. Read requires `milton:read`; write additionally requires `milton:write`. Refresh cannot widen the original binding. Once the rate gate admits a UserInfo request, the wrapper also requires the token's binding to be live by `milton_guard.binding_status`, as MCP and the app do on every call (a JWT's binding, subject, client `azp`, scopes, incarnation and generation read from its claims, whose signature native then verifies; an opaque token, the app's included, looked up by its stored hash); otherwise 401 `invalid_token` with no claims and native is not called, and a database failure is 503. A disconnect or a begun deletion therefore ends UserInfo at once, not at the token's expiry. The consent form offers Read only or Read and write and explains that each exact memo still needs the person's approval. Scope does not prove conversation approval.

Public registration always strips browser cookies and refuses initial-access Authorization credentials. It cannot create user-owned clients, privileged resources, skip-consent flags or outbound logout configuration. Actual token authentication is native and bound to the registered method. The mounted discovery documents project the supported public profile: none/basic/post token authentication, post-only own-client introspection, basic/post revocation, no DPoP, no back-channel logout. Assertion/key-based client auth, custom claims requests, PAR/JAR, arbitrary metadata, token binding and untrusted end-session controls are refused. Native server-only client/resource/consent/user deletion paths are unavailable over HTTP and guarded against runtime SDK calls without request context. No native admin console exists.

CIMD uses the upstream Node public-address/DNS-pinned transport and accepts any `https` metadata URL on a DNS host without credentials or fragment (no IP literal or `localhost`), such as Claude Code's `https://claude.ai/oauth/claude-code-client-metadata` and Muse's `https://platform.muse.ai/oauth/client-metadata.json`; dynamic registration is already public. Informational `client_uri` may differ; functional post-logout origins remain bound. Exact native callback/resource/S256 checks and consent stay enabled, and consent shows the full client ID URL, so its host is visible. No remote logo is rendered. No raw fetch fallback is supplied.

## Public account behavior

Auth pages: `/login`, `/signup`, `/verify`, `/forgot-password`, `/reset-password`, `/consent`, `/security`. Forms use native handlers through a same-origin adapter. Native success destinations from the form adapter, including same-origin authorize hops, and direct native URL-encoded browser form POST redirects (including logout confirmation) share a fresh HTML document with an escaped meta-refresh and visible Continue link; strict `form-action 'self'` stays enabled. Native proof/redirect validation still selects the destination; the adapter creates no redirect or session authority. Direct native GET redirects, JSON/fetch responses and machine URL-encoded calls retain native status, Location and body. Deferred email changes, user update/delete, direct consent mutation, MFA, passkeys, magic links, organizations, provider-token access and admin routes are denied. Verification GET does not sign in. The original native reset-link GET validates and redirects to the form without consuming its proof; native reset consumption/hashing happens on POST. Expired links give a new-request route. Native mail callbacks capture one exact original message without provider I/O. Generic signup/reset/resend responses commit a common encrypted job or no-op receipt before returning200, including social registration that sends verification. Native proof commits and mail acceptance are separate;503 means uncertain/retryable, not proof of rollback or delivery. Successful acceptance does not mean mail arrived. If signup acceptance fails after native commit, recover through verification resend; request a new link after reset uncertainty. Small native database timing differences remain; uniform timing is not claimed.

Google and GitHub use native web callbacks, verified email and explicit linking. No implicit email merge is allowed. The native user ID remains stable when a method is linked. Fresh proof, a live original session/fence and another working method protect unlinking; the parent is locked before the child delete. Unlink advances generation and ends browser/AI authority. Before unlink enters its native transaction, an authenticated app handoff preserves current native eligibility metadata for an existing writing account only; failure prevents removal, expired billing is irrelevant, and native-only users are never admitted. First social password uses native email recovery. All generation advances and deletion atomically retire earlier reset proofs; issuance validates the original native user snapshot under the parent lock, so a delayed request cannot recreate stale recovery authority. Password changes always rotate the current session, end other sessions and invalidate old app/AI bindings. Native session listing is sanitized to remove reusable tokens; the security UI addresses sessions by ID and resolves an exact owned token inside auth for native revocation. Session revocation ends selected browser authority while offline AIs remain connected. Account deletion stays app/Stripe/data orchestrated.

Password policy is 15–128 Unicode code points in both original and native NFKC forms, with spaces preserved and no truncation. Native Better Auth 1.7.18 scrypt performs NFKC; equivalent forms share a password. A local, pinned normalized common-password hash list screens candidates without network transmission; provenance/license are in [THIRD_PARTY.md](THIRD_PARTY.md). It is not an exhaustive compromise database. Upstream Google/GitHub access/refresh/ID tokens are discarded by supported native database hooks after callback validation; no provider token is saved in an account cookie. The signing-key table remains native encrypted storage under AUTH_SECRET. Native code-unit maximum 256 accommodates 128 astral characters; the endpoint hook enforces the actual 128-code-point ceiling. Original and normalized expansion bounds are both checked before expensive hashing.

## Service configuration and secrets

All selected capabilities must be configured at startup:

- `AUTH_DATABASE_URL`: auth-only runtime login, verified certificate/hostname TLS even with mode omitted, pool maximum 8, bounded connect/query/statement timeouts (through Neon the 5-second statement limit is the role setting in [`007-role-timeouts.up.sql`](../../server/migrations/007-role-timeouts.up.sql), since Neon drops connect-time settings); never the migration owner.
- `AUTH_SECRET`: stable native cookie/token encryption secret shared across auth instances.
- `AUTH_ADMISSION_SECRET`: separate bearer credential for auth's calls to the `milton-admit` service.
- `AUTH_ADMISSION_URL`: the `milton-admit` origin. A `https://…run.app` origin (the only one production accepts) makes each call carry a metadata-server Google ID token for that origin in `X-Serverless-Authorization`, cached until five minutes before expiry; a loopback `http://` origin (development and tests) carries none. Not a secret: a plain environment variable on the service and the mail job.
- `AUTH_RATE_SECRET`: separate stable HMAC key for shared network/account buckets.
- `AUTH_APP_CLIENT_ID`: the owner-provisioned first-party app ID. The app alone receives its client secret.
- `AUTH_GOOGLE_CLIENT_ID`, `AUTH_GOOGLE_CLIENT_SECRET`, `AUTH_GITHUB_CLIENT_ID`, `AUTH_GITHUB_CLIENT_SECRET`.
- `AUTH_RESEND_API_KEY`, `AUTH_MAIL_FROM`: selected sender at `notifications.meetmilton.com`.
- `AUTH_MAIL_REPLY_TO`: optional, default `support@meetmilton.com`; must be one email address. Every auth message carries it as Resend's `reply_to`, so a reply reaches support instead of bouncing off the sending address. It has a default rather than being required because it is one public address, the same in every environment, so a release needs no new variable; set it only to send replies elsewhere. The plain-text body is unchanged.
- `AUTH_TURNSTILE_SITE_KEY`, `AUTH_TURNSTILE_SECRET_KEY`: optional, both or neither (one alone fails startup). With both, Cloudflare Turnstile guards email sign-up: `/signup` loads `https://challenges.cloudflare.com/turnstile/v0/api.js` and renders the widget (action `signup`) in the email form, and only that page's CSP adds `https://challenges.cloudflare.com` to `script-src` and `frame-src`; the form adapter forwards the widget's `cf-turnstile-response` as `x-captcha-response`, never a header the browser sent. The wrapper verifies it itself, after the network gate and before native. A sign-up without a well-formed `email` answers 400 `invalid_email` before any database work or Cloudflare call, so every check spends the per-email bucket; the 320-character ceiling is the wrapper's own (mail capture's bound on a recipient, RFC 5321's path limits), not native's, so with Turnstile on a longer address native would accept is refused. The gate also takes a per-network sign-up bucket of 3 in 10 s before the check, so one network cannot keep the verification slots busy, and native's own `/sign-up/email` rule is off then, so that bucket is the only sign-up limit (two offset windows would extend a shared network's lockout). With Turnstile off, native's rule applies as before. Then it gives back its native in-flight slot, posts only the secret and token to siteverify (no `remoteip`: auth knows only an IPv6 client's /64, and the field is optional), waits at most 5 s with at most four verifications at once per process, and requires success, hostname `auth.meetmilton.com` and action `signup`, then takes a slot again. A missing token answers 400 `captcha_required`; a token over 2,048 characters, Cloudflare's `invalid-input-response`, `timeout-or-duplicate` or `missing-input-response`, or a pass for another host or action answers 403 `captcha_refused`. The answer must have the documented shape: `success` a boolean and, on failure, `error-codes` an array of strings. Anything else (`internal-error`, a secret error, any other code, a malformed answer, a non-2xx, a network failure or the timeout) is a retryable 503 `captcha_unavailable` and logs `auth_turnstile` with only Cloudflare's documented code names, `other` for any other code, or a fixed label (`malformed`, `http_error`, `network`, `timeout`): it fails closed, and nothing is created. A fifth concurrent verification answers 429 `busy_retry`. Because verification holds no native slot, a slow or failing Cloudflare stops only email sign-ups: sign-in, resends, resets and Google/GitHub sign-up keep their capacity. Better Auth's captcha plugin was not used: it waits up to 10 s inside a native slot, turns every `success:false` (Cloudflare's `internal-error` too) into 403, and sends the /64 as `remoteip`. The site key is public (a plain token, rendered in the page); the secret belongs in the encrypted auth payload. Without them, sign-up needs no token.
- `PORT`, default 8080.

Before listening, startup checks that the database login is exactly the safe `milton_auth_runtime` role. A connection failure (connect timeout or drop, `ECONNREFUSED`, `ECONNRESET`, `ENOTFOUND`, `ETIMEDOUT`, PostgreSQL `57P01`/`57P03`) retries after 0.5, 1, 2, then 4 seconds for about 15 seconds, logging one `auth_startup_retry` line with the attempt, delay, error class and code only; then startup fails. A role or privilege refusal fails startup at once.

`AUTH_ENCRYPTED_ENV_FILE` optionally names the mounted encrypted auth-only payload; dotenvx decrypts it with the separate platform `DOTENV_PRIVATE_KEY`, with external/native secret helpers disabled and no value logging. Three distinct dotenvx payloads/platform keys remain the selected secret boundary. The release owner supplies auth's decrypted environment through its existing approved secret injection. This source never reads a retained key. Never copy plaintext `.env*` or a platform key into an image. Never run auth with the app/MCP/Stripe payload.

Mail delivery is a separate bounded command, never a public route or request-driving task. Only native code creates/verifies proofs. `AUTH_SECRET` also derives a separate mail key through native `makeSignature` (HMAC-SHA256 domain `milton auth mail v1`, internally native `getCryptoKey`); native symmetric utilities use a version1 `$ba$1$` envelope. The authenticated encrypted payload binds the job UUID, exact original destination/URL/kind/user/incarnation/generation/expiry and full provider message, including sender. Retries use that exact body and the job UUID as Resend Idempotency-Key. There are no raw recipients, links or proofs in queue columns/logs. Current native `getCryptoKey` is an HMAC importer, not a symmetric key converter.

Back up the protected original auth secret with the selected database recovery material. Changing it without the matching prior key makes pending messages terminal unreadable on claim; ask for new links. No implicit legacy-key fallback or new key setting is added. A restore can also resurrect old native authority: closed ingress and the existing security-fence reconciliation remain mandatory. Do not restore only mail data or switch to an unrelated key to hide recovery problems.

Owner must verify sender, effective sending permission/quota, SPF/DKIM/DMARC and bounce behavior through an explicitly authorized controlled send. This build performs none. Resend documents24-hour keyed deduplication; crashes or remote-success/local-timeout remain ambiguous within vendor semantics, never universal exactly-once delivery.

At most four requests can enter native work concurrently per auth process. Every rate limit below is an atomic shared bucket in `milton_guard.take_rate`, keyed by HMAC-SHA256 with `AUTH_RATE_SECRET` (no plain address, email or client is stored). The wrapper decides in one statement: first the gate (the network bucket, or the app's own ceiling when the request proves it is the app), then, only if the gate admits, the request's other wrapper buckets. A request the gate refuses creates and charges no other bucket. The wrapper answers `rate_limited` 429; native decides its rules through `rateLimit.customStorage`, one `take_rate` call each, and answers its own 429. Windows are fixed, starting at a bucket's first hit.

The app proves itself by its client secret (token, introspection, revocation) or by presenting one of its own access tokens (UserInfo), each compared with native's stored SHA-256/base64url hash inside the same statement. A token proves it only while native would still accept it: unexpired, unrevoked, its client enabled, its session (if any) live, and its binding current by `milton_guard.binding_status`, so a password change or disconnect ends it. The token is read with native's own `parseAccessTokenAuthorization`, so both see the same token however the header is spaced. A request that only names the app takes the ordinary buckets.

A client or token that is named but not proven spends only the caller's own address's buckets, because every scoped key includes the network. The network is the client address Google's load balancer appends, the second-to-last X-Forwarded-For entry (IPv4-mapped IPv6 as IPv4, other IPv6 by /64), the same rule MCP uses; the first entry is never trusted. Without a well-formed pair (local runs, internal callers) the socket peer is used. ## Schema and owner operations

Separate NOINHERIT roles: `milton_auth_runtime`, `milton_app_runtime`, `milton_mcp_runtime`; separate NOLOGIN `milton_auth_owner`. [000-owner-prerequisites.sql](migrations/000-owner-prerequisites.sql) is a reviewable preparation plan. It is not permission to alter a live shared database. Audit source schema, inherited/default/PUBLIC grants, views/SECURITY DEFINER functions, ownership/DDL/TEMP and retained managed-auth access before granting login. App-only token/session/flow tables must have their own explicit grants; MCP cannot inherit them through a writing role. `checkRuntimeRole` in [src/roles.ts](src/roles.ts) checks effective runtime rights with each real login; actual production names/schema inventories remain a release gate.

Migration order is native001, credential002, reference/lifecycle003, product004, recovery005, mail006, connection-key status007, deletion links008, then the app builder's storage/mapping migration. 007 adds only `milton_guard.connection_key_status`, executable by MCP and app; it reads no credential columns and changes no auth runtime code. Native001 was generated from the pinned public migration planner and checked into source; startup never generates/executes SQL. 002 gives old native users default incarnation/generation/revisions and leaves old sessions unstamped/refused. `milton_credential.fence_ids` is owner-only and noncycling. The runtime cannot read, allocate directly or rewind it. No managed `neon_auth` table/data is modified. Qualified SECURITY DEFINER functions use `pg_catalog, pg_temp`, explicit grants and protected columns; mechanism tables have no runtime CRUD grants.

After snapshot and explicit selection, an owner with the exact owner role may run:

```sh
node --experimental-strip-types apps/auth/scripts/migrate.ts up --apply
node --experimental-strip-types apps/auth/scripts/provision.ts --apply /private/owner/output.json
```

All runtime and owner migration/provision/maintenance pools force verified TLS. Omitted mode is safe; `sslmode=require` is upgraded to full certificate/hostname verification, and `verify-full` is accepted. Unsafe modes (including verify-ca), duplicate query options, `ssl`, libpq compatibility, client certificate/key options and ambiguous TLS keys refuse. `sslrootcert` may name an explicitly selected public CA; a disposable child can use `NODE_EXTRA_CA_CERTS` without changing system trust. No insecure environment override is supported. These commands require `AUTH_OWNER_DATABASE_URL`; provisioning additionally requires auth configuration. The provisioner uses native anonymous registration/secret hashing, then atomically promotes exactly one confidential identity-only app client and stores its first-party policy. It creates no human user. Output is an exclusive mode-0600 file outside the repository; never paste it into reports. Install the client ID in auth and ID/secret in app, using separate numeric secret versions. Repeat provisioning refuses when a fixed app exists; key/client rotation is a separately reviewed owner operation. Owner credentials never enter runtime.

There are no down migrations: the rollback is the snapshot taken before every migration, restored with a compatible revision. Recovery005 retires pre-upgrade reset proofs because they lack original issuance provenance. Apply with only compatible fixed writers; an older writer cannot safely issue recovery across this upgrade. Snapshot/restore and data reconciliation are separate production operations, never implied by build tests.

## Live authority, admission and lifecycle

The single reference authority is `milton_guard.authorization_binding`. Native user fences/session snapshots and exact credential CAS remain separate from library protocol state. The public Kysely adapter is decorated for credentials and original-reference cleanup at outer, reconstructed and nested transaction levels. Native token lookup captures immutable subject/client/reference before child-write transaction entry; parent locks are taken on the same Read Committed executor. A zero-row CAS throws; after-commit native errors cannot undo a committed fence.

Auth uses original validated native identity metadata (verified email and stable Google/GitHub subjects) only for app-owned trial fingerprints. Successful explicit linking makes an awaited idempotent admission handoff; app-only security status also supplies current verified metadata so deletion can preserve eligibility after an uncertain link notification. Fingerprints never establish account ownership or enter AI claims. Auth calls authenticated `POST <AUTH_ADMISSION_URL>/internal/auth/admit` (the `milton-admit` service, off the public load balancer) only after native validation; an admission it answers 410 (the account's deletion has begun) is a final 403 `account_deleting` on every admitting path (authorize, consent and the explicit-link handoff), any other refusal a retryable 503. An explicit link refused this way stays linked natively, as a link whose handoff fails does. App owns stable exact issuer/subject mapping, trials/billing and deletion fingerprints. No email-based ownership merge occurs. Exact contracts and final migration function signatures are recorded in the parent task's `auth-product-interface.md`. SQL false/NULL means refusal; SQL failure means retryable outage, never a stale positive fallback. MCP checks binding live on every tool use; app also checks original sid/incarnation/generation and unexpired native session on every local-session use.

App durably persists one UUID lifecycle operation before the first call. `begin_operation` captures the original incarnation and at most 256 immutable references under a parent lock, commits refusal before cleanup, and bumps the generation for deletion. `cleanup_operation` removes at most 16 rows per native table per call and never re-resolves current connections. Native refresh/access FK dependencies are explicitly drained before parent deletion. Sessions are capped at 64/user and methods at 8/user; binding capture at 256/user. Unknown owned-client/unbound OAuth cascade inventory refuses deletion and requires owner reconciliation. Public DCR never owns clients; no native client-management route is enabled. Deletion008: once the account's codes, tokens and consents are gone, each call also takes up to 16 of the account's `milton_guard.client_link` rows (written by `consent_gate`, removed by nothing else) under the registration's row lock, deleting an anonymous registration no other account links and otherwise clearing its `name` and `contacts`, and either way recording the SHA-256 of its client ID in `milton_guard.cleared_client` (no foreign key), which the `keep_cleared` trigger enforces on every insert or update under that client ID, then sessions and methods; once none of those or of its links remain, one step deletes all its bindings (at most 256, `bind_flow`'s cap) with the user (whose foreign key from the links refuses an earlier delete). Retried complete operations retain the tuple indefinitely but clear the target array; this minimal idempotency record prevents a stale disconnect from capturing a newer connection. It contains no credential or writing. Do not delete operation tombstones or rewind the allocator.

Maintenance is owner-operated, bounded and scheduled separately: `cleanup_expired(1..64)` removes expired session/verification/rate rows after a day of grace without touching offline references. The same owner-only function drains expired access/refresh/consent rows before dropping expired bindings, preserving FK bounds, active offline references and incomplete operation targets. Native cleanup selects at most64 rows per native table, with parent locks for native child cleanup and one native maintenance transaction at a time. ## Bounded mail delivery and retention

No mail is ever queued for an address on the reserved `.invalid` top-level domain (`reservedRecipient` in [src/mail.ts](src/mail.ts)), such as the fictional end-to-end test account: a reset, verification or any other message for one commits the same no-op receipt an unknown address does, so the public answer is unchanged and the delivery job has nothing to send. Fixtures that need real queued mail use `example.com`.

Nor is mail queued to a domain that DNS says takes none ([src/mail-domain.ts](src/mail-domain.ts)), so junk sign-ups do not hard-bounce against the Resend reputation or take queue slots: a null MX (RFC 7505), NXDOMAIN, or no MX and no A/AAAA (the RFC 5321 §5.1 fallback) commits the no-op receipt. The lookup is a fresh `node:dns/promises` `Resolver` (1-second timeout, one try per query) cancelled after 2 seconds in all, and a timeout, SERVFAIL or any other resolver error sends, so a DNS outage never stops a real person's mail. The requested address's domain is looked up even when native captured no message, so an unknown address waits for the same lookup as a known one. Native's work is done by then, so the request gives back its native in-flight slot first: a domain an attacker serves slowly holds a request for up to 2 seconds but none of the four slots. A skip logs one `auth_mail_skipped` JSON line with the kind and the first 12 hex digits of the domain's unkeyed SHA-256: an operator can check a domain someone names by hashing it, and no personal domain is written in clear. Tests inject the lookup (`boundaries.mailDomain`); none uses real DNS.

Why a queue, not inline sends (decided 2026-11-07, dropped TODO #26): sending during the request makes existing accounts answer measurably slower than unknown addresses, which reveals who has an account; sending after the response is unreliable on Cloud Run because CPU is throttled once the response is sent. The outbox gives every address the same database write and the same answer, retries through Resend outages, and cancels a queued reset after a security change.

```sh
# Default dry run: no environment, database or provider access.
node --experimental-strip-types apps/auth/scripts/deliver.ts
# Later selected auth-only runtime operation (not owner credentials):
node --experimental-strip-types apps/auth/scripts/deliver.ts --apply
# Compiled/container equivalent, same auth-only environment:
node deliver.js --apply
# Separately selected owner-only expiry maintenance:
node --experimental-strip-types apps/auth/scripts/maintain.ts --apply
# Compiled/container equivalent, same separate owner environment:
node maintain.js --apply
```

The auth image includes `deliver.js` and `maintain.js`; its default service command stays `cloud-run.js`. Delivery uses a verified-TLS pool of1 with3-second connect,5-second statement and6-second query limits. It considers at most16 candidates, one claim at a time, with `FOR UPDATE SKIP LOCKED`; it commits the2-minute lease/attempt before external I/O and holds no database lock over network. It stops starting work23 seconds before a90-second pass deadline, allowing bounded connect/query/network/finish completion. Native cryptography handles only a bounded40,000-character ciphertext. The prepared job has one task, no platform retries and180-second outer timeout including runtime-role checks. These are execution bounds, not an account/product cap.

Each original job has at most5 claims, backoff1/2/4/8 minutes and a five-second `redirect:error` send timeout. The15-minute delivery deadline often permits fewer attempts. A crash can consume a claimed attempt. Shared429 pause persists Retry-After (seconds/date), clamped to60 seconds–24 hours by the worker; SQL independently caps completion delays and the stored shared pause at24 hours. A valid3000-second pause still outlives individual messages, stops the pass, and leaves later unclaimed work's budgets untouched. Once pause ends, other unexpired work can resume; jobs past their own expiry cannot send. Concurrent already-in-flight work cannot be recalled. A claimed send may race security change. Sending never mints or refreshes authority;005 immediately retires affected native reset proofs. Claim/finish target original job/fences only, never a new email lookup. Missing/deleted/recreated users, generation changes and verified emails fence the relevant queued message. No native-user FK/cascade adds unbounded deletion work.

`accept_mail` accepts either one encrypted native message or a NULL no-op, under the same auth-only EXECUTE grant. Native capture validates the original identity, token/URL and finite, future, at-most-one-hour lifetime against the native process clock. SQL requires finite proof expiry later than its own clock and independently caps delivery at15 minutes/native expiry; it does not compare the native one-hour lifetime against the database clock. This trusts only the auth runtime to submit native captures, not arbitrary public expiry fields. Extreme skew can still put native expiry behind the database clock (acceptance refuses), or a database delivery deadline behind the worker clock (delivery refuses); clock alignment remains an operating prerequisite, not a new authority or lifetime extension. `claim_mail` accepts1..16 candidates; `finish_mail` affects one UUID+lease, with terminal payload clearing. No runtime has direct CRUD on `mail_job`/`mail_delivery`; app/MCP have no mail function execution. All functions have qualified storage and fixed `pg_catalog,pg_temp` search paths. Owner `cleanup_expired(1..64)` preserves native cleanup, scans at most that many pending mail candidates to expire/fence/clear, and deletes at most that many terminal/no-op receipts eligible after24 hours. There is no broad sweep in claim or finish.

Delivery expires at the earlier of original native expiry and15 minutes after acceptance. Terminal sent/failed/fenced/expired states clear ciphertext immediately. **Physical expiry clearing needs bounded claim/maintenance; disabled/backlogged maintenance can retain encrypted contents longer.** Receipts carry original user/fences/kind/times but no recipient/link and become eligible for deletion24 hours after acceptance; actual removal also depends on maintenance. Stateless verification expires after1 hour. Remaining native verification records are eligible for cleanup1 day after expiry;005 retires reset rows immediately on security change/deletion. Backups and vendor copies have separate retention.

### Throttle inspection and recovery (prepared, not enabled)

Each pass logs one JSON line, `{"message":"auth_mail_pass","claimed":…,"sent":…,"retry":…,"failed":…,"throttled":…}` (counts only), which Cloud Logging stores as `jsonPayload`, and each send that ends failed or throttled logs one more, `{"message":"auth_mail_send","outcome":"failed"|"throttled"}` ([src/mail-log.ts](src/mail-log.ts)). The page policy `milton-auth-mail` ([server/deploy/monitoring](../../server/deploy/monitoring/milton-auth-mail.policy.json)) emails on 3 or more of those combined in 15 minutes, through the log metric `milton-auth-mail-problems`. Each throttle also logs the pause it sets, `{"message":"auth_mail_pause","seconds":N}`, and one pause over 900 s (the delivery lifetime, so every queued message would expire; a daily or monthly quota 429) pages on its own through `milton-auth-mail-long-pause`. The prepared operator check of the shared pause and aggregate pending/expired counts is below. A paused pass can report zero claimed/throttled, so silence after the first429 is not evidence of recovery. Do not add message bodies, recipients, proof URLs or credentials to logs.

The24-hour cap is an operational safeguard aligned with Resend's documented daily quota reset at midnight UTC. Resend also documents429 for monthly quota exhaustion and request rate limits; the cap does not establish this account's plan/quota or guarantee vendor recovery. Persistent monthly exhaustion requires operator reconciliation before resuming delivery. See [Resend errors](https://resend.com/docs/api-reference/errors).

Only an authorized operator, using the separate delegated NOINHERIT owner login over verified TLS, may inspect/reset the pause after independently verifying recovery. Keep `milton_auth_owner` NOLOGIN, explicitly assume it with `SET ROLE`, and never give its credentials or membership to delivery/auth/app/MCP runtimes. Disable SQL history and keep connection credentials outside command arguments/logs. The following is a prepared procedure, not a selected live action:

```sql
SET LOCAL ROLE milton_auth_owner;
SET LOCAL statement_timeout = '5s';
SELECT current_user, session_user;

FROM milton_guard.mail_delivery WHERE singleton;
SELECT count(*) FILTER (WHERE expires_at > clock_timestamp()) AS unexpired,
       count(*) FILTER (WHERE expires_at <= clock_timestamp()) AS expired
FROM milton_guard.mail_job WHERE state = 'pending';
ROLLBACK;
```

Verify provider recovery privately from the relevant rate/quota/reset evidence before any reset; do not infer recovery from24 hours passing. Coordinate delivery passes so an already-in-flight429 is not being cleared. Record the inspected `paused_until` as a psql variable `observed_pause` (timestamp only), then use the same owner connection:
