# Honcho and Milton: product comparison

Research date: **2026-11-05**. This is a dated assessment of public pages and source, not a continuously updated competitor page. Prices, claims and observed site copy refer to that date. Milton’s behavior comparison uses the shipped `fec8802` runtime and the public site observed during the review. Recommendations and the proposed experiment are not approved work or product commitments. See also the [focused source teardown](honcho-source-2026.md).

**Assessment.** Honcho is a substantial overlap, not a facts-only memory product we can dismiss. It already offers person modeling, communication-style recall, correction learning and memory shared across agents. Its Hermes distribution also reaches people using an existing assistant, so “developer infrastructure versus consumer product” is an incomplete distinction. Milton’s credible current distinction is a writing-specific workflow built around selected, exact, person-approved examples and rules. That is a useful product choice; it is not yet a demonstrated advantage in editing time or a defensible technical moat.

My recommendation is to keep Milton focused on the next email, DM or Slack message, make the approved-example mechanism concrete, and measure the first draft through the person’s final edit. Do not add Honcho’s background inference, embeddings or memory graph. The strongest immediate lesson is its clear explanation of what reaches the assistant and how to check it. The largest missing evidence is ours: whether Milton improves on giving the same assistant a small Markdown file of approved examples.

**Evidence standard.** “Observed” below means a public HTTP response or public source I actually read. “Documented” means the vendor describes a mechanism; it does not mean I exercised its hosted implementation. “Claim” means marketing or vendor-reported evaluation. “Inference” is my assessment. No Honcho account, installation, authenticated dashboard, live memory ingestion or writing upload was used. Milton’s authenticated behavior was not independently reproduced in this review. This is a content, workflow and architecture review; responsive rendering and interactive onboarding were not visually tested.

**What problem Honcho owns.** Its core job is to help an agent preserve and reconstruct an evolving understanding of people and other entities across interactions. Developers supply messages; Honcho derives reusable knowledge; the application injects retrieved context into its chosen model. It is explicitly broader than storage or factual recall. That scope includes preferences, inferred patterns and multiple participants’ differing perspectives. [Product overview](https://honcho.dev/docs/v3/documentation/introduction/overview).

The business has two entry points: builders adding memory to their products, and users adding memory to an agent they already run. The latter matters to Milton. Honcho’s Hermes page sells reduced repetition, learning recurring fixes and briefing the agent before replies; it labels its sample interaction illustrative. Its usage and adoption counters are vendor claims, not independent proof of writing improvement. [Hermes landing page](https://honcho.dev/hermes). General integrations are presented as sharing a workspace across tools. [Integrations](https://honcho.dev/docs/v3/guides/overview). A shared configuration file alone does not establish shared memory: the tools must use the same workspace and person identity; documented host defaults can keep workspaces separate. [Claude Code configuration](https://honcho.dev/docs/v3/guides/integrations/claude-code).

The API and worker split, PostgreSQL input storage and vector-backed derived knowledge are documented in the [architecture](https://honcho.dev/docs/v3/documentation/core-concepts/architecture). The public source also contains message embedding and observer/observed collection models. [Storage models](https://github.com/plastic-labs/honcho/blob/main/src/models.py). These mechanisms support general agent continuity; none alone proves fewer stylistic edits.

**Where Honcho already addresses style and corrections.** The homepage explicitly offers a communication-style question at its medium reasoning tier. [Homepage](https://honcho.dev/). More decisively, the actual MCP instructions give communication preferences and formality as example questions, and describe how to trace a conclusion’s sources before correcting it. They distinguish recall from recording: if the user has not asked to record the conversation, the assistant should remain in recall mode. Therefore, portraying Honcho as having no consent boundary would also be unfair. Its memory-store mode records exchanges and derives knowledge; it does not specify Milton’s separate approval of every retained writing example and its context. [MCP instructions](https://github.com/plastic-labs/honcho/blob/main/mcp/instructions.md).

A useful distinction in those examples: how an assistant should speak **to** a person is not automatically how it should write **as** that person to someone else. Audience, purpose, relationship and message structure can change the voice. Milton explicitly stores examples for that second task; whether its context labels improve the resulting draft still needs testing. This is a narrower hypothesis than claiming Honcho cannot model writing style.

The Hermes documentation explicitly lists communication style among learned user attributes, supports prompt-time injection, and exposes a durable-conclusion tool that can write, list, search and delete knowledge. [Hermes integration](https://honcho.dev/docs/v3/guides/integrations/hermes). Honcho’s own correction explanation says a correction creates a new timestamped conclusion and dreaming later removes the outdated one. This establishes a documented correction mechanism, not evidence of consistent stylistic transfer after a correction. [Honcho’s mechanism explanation](https://honcho.dev/vs/mem0) — used here only for its description of Honcho, not as authority about the other vendor.

I did not find a demonstrated end-to-end workflow in the inspected material that chooses a person’s approved email/DM examples, preserves exact approved context, drafts a new message and measures that person’s edits. That is an evidence gap, not proof Honcho cannot support it. A developer could build curation and approval around its raw messages and metadata, or disable observation for selected inputs. Milton’s differentiation is the workflow and contract already chosen, not exclusive access to a storage primitive.

**Milton’s current product, checked against source.** The live homepage focuses on writing from approved examples, with email/DM setup and a separate offer to retain a final draft. It labels its demo fictional and says editing results are unmeasured. Public reads of the homepage, pricing and setup returned 200, redirecting to `www.meetmilton.com`; the web search reader failed on these URLs, so I used unauthenticated HTTP and parsed the HTML. [Live homepage](https://www.meetmilton.com/), [setup](https://www.meetmilton.com/setup).

The implementation has four MCP tools, five report families and per-person sample kinds. `get_report` requires intent and selects up to eight active examples by requested kind, purpose overlap, matching context dimensions, lexical relevance, recency and ID. It fills remaining slots with broader examples, reports match signals and exposes all active kinds, including those outside the eight selected. Context distinguishes whole works from excerpts; optional unknown values remain absent. Sample-context correction preserves the body and identity and advances version fencing. There is no model call in storage or assembly. [Reports](../../server/src/store/reports.ts), [context shape](../../server/src/store/sample-context.ts), [save/read contract](../../server/src/store/compiled.ts).

Those are current mechanisms, not validated voice-quality gains. Exact edits and immutable sample bodies rule out a server rewrite of approved prose. The external assistant still interprets meaning, chooses what to submit, and decides whether to read and follow guidance. Per-save retention approval is an instruction to that assistant; Milton cannot independently observe the person’s yes. [Served instructions](../../server/src/mcp.ts), [SPEC](../../SPEC.md).

The comparison uses the shipped structured-context, kind-aware retrieval and context-correction contracts. Earlier design proposals are not evidence of the current implementation. Public contracts are recorded in the [SPEC at the reviewed runtime](https://github.com/zoneofdanger/milton/blob/fec88029f86cf6c71710fa78978c35269becb718/SPEC.md); no private account was accessed for this review.

**What the site and onboarding do well.** These are observations of public content and documented paths, not conversion or usability measurements.

- Honcho puts mechanism and proof close to its promise: a short input → memory → context loop, recognizable integrations and links to evaluation details/source. Its main page is broad; its Hermes page is more effective at showing one person, one familiar assistant and what context changes before an answer. Milton should borrow that concrete demonstration for a writing task, with an illustrative label until measured. [Homepage](https://honcho.dev/), [Hermes page](https://honcho.dev/hermes).
- It separates inexpensive context retrieval from questions needing more reasoning. That helps a builder choose an operation. Milton’s equivalent clarity is “these approved examples reached the assistant for this situation,” using its existing sample IDs and match explanation. No new inference layer is required. [Context](https://honcho.dev/docs/v3/documentation/features/get-context), [chat](https://honcho.dev/docs/v3/documentation/features/chat).
- The SDK quickstart supplies a bounded dataset and expected question; the integrations include a concrete check after setup. The useful pattern is a check that demonstrates the intended job. For Milton, a successful connection should lead promptly to drafting the person’s next message, while keeping connection success distinct from voice quality. [Quickstart](https://honcho.dev/docs/v3/documentation/introduction/quickstart), [MCP verification](https://honcho.dev/docs/v3/guides/integrations/mcp).
- Evidence can be requested from what the reasoning agent actually read. Honcho explicitly warns that this over-reports: exposure is not proof of reliance. Milton can apply that distinction today when showing selected examples; a successful read is not evidence the draft used them well. [Evidence contract](https://honcho.dev/docs/v3/documentation/features/advanced/evidence).

For Milton, approval of a context-specific example, a successful relevant read, and a person editing the resulting draft can improve or test writing voice. A heartbeat, a session summary or “it remembers my project” only demonstrates continuity. Keep those outcomes separate in the product and evaluation.

**Proof and weaknesses, including ours.** Honcho’s published evaluation page reports 90.4% on LongMem S and 89.9% on LoCoMo, plus BEAM results through 10M tokens. Those are vendor-reported memory/reasoning benchmarks. The page identifies different models/configurations, notes benchmark limits, and reports weaknesses such as abstention; it is not an email-voice or editing-time study. I inspected the linked repository’s README and result inventory, not the full multi-megabyte traces, and did not rerun it. [Evaluation](https://honcho.dev/evals/), [result repository](https://github.com/plastic-labs/honcho-benchmarks).

Neuromancer XR’s research page describes a Qwen3-8B fine-tune for deriving conclusions and an older LoCoMo experiment; the model-series page marks MR as still in training. The current eval page instead describes Gemini/Haiku defaults and managed-service variation. Do not attribute every headline score to one currently deployed custom model, or treat “formal logic” as a formal correctness guarantee. [XR research](https://plasticlabs.ai/blog/research/Introducing-Neuromancer-XR), [model series](https://plasticlabs.ai/neuromancer), [evaluation configuration](https://honcho.dev/evals/).

Honcho’s continuity story has real lifecycle qualifications. Deleting a session does not erase all derived knowledge; some conclusions survive and require separate removal. Its docs disclose that explicitly. That matters when a person withdraws a writing example: derived style judgments can outlive the originating conversation. This is a documented lifecycle tradeoff, not a claim of an observed leak. [Deletion semantics](https://honcho.dev/docs/v3/documentation/features/advanced/deleting-data). Broad claims about remembering everything, universal improvement or solved statefulness outrun the writing evidence inspected here.

Milton’s public notes report fictional-writer draft scores of 3.77 for newest examples, 3.72 for its then-current ranking and 3.68 for embeddings plus ranking. Better retrieval did not improve those drafts. These are model-scored synthetic experiments, not evidence that recency is best for real people, and not validation of the newly shipped context/kind policy. Real-person ratings, editing outcomes and voice performance across assistants remain open. Keep the negative result visible. [Public notes](https://www.meetmilton.com/notes), [underlying ranking research](sample-ranking-2026.md).

The review found a dated discrepancy in Milton’s live copy on 2026-11-05: the privacy page says a newer sample of a kind automatically retires its predecessor and directs removals to email support. Current source keeps samples until explicit replacement/removal and exposes `retire_samples` through the assistant. Recheck the current policy and source before scoping a correction; this observation does not assert the discrepancy remains today. [Live privacy page](https://www.meetmilton.com/privacy), [current save contract](../../server/src/store/compiled.ts), [behavior inventory](../how-milton-works.md). The privacy page’s separate wording about storing compiled reports also deserves reconciliation with on-read assembly. This is a copy/behavior comparison, not legal advice.

**The strongest skeptical HN response.** The following is my constructed challenge, not a quotation from a commenter:

> You host some approved examples and Markdown instructions behind MCP for $5.01. Any model can imitate a few examples already. A synced file can carry those examples between agents, and Honcho can retain originals, learn preferences and inject context automatically. Your exact editing, version tokens and history are good engineering, but none proves the email sounds more like me. Your own synthetic study did not show better drafts from better retrieval. Why should I pay to curate another store and remind an assistant to read it? Exportability is good for users, but it makes a “data moat” story weaker. Show that your curation and delivery save enough editing time, including setup, to be worth a recurring bill.

That critique largely stood at the review date. “One voice everywhere,” MCP, exact storage, user-owned data and sample count are easy to copy. A person’s collection can become valuable without becoming a defensible moat: export is a feature, and the writing should remain theirs. The plausible advantage is consistently turning a few selected examples into useful first drafts across everyday contexts with little maintenance. It becomes credible through observed outcomes and distribution, not by naming the store a new category.

Evidence that would change my assessment: blinded first-draft editing time and stylistic edit burden improve against the same examples supplied as Markdown; the gain survives a second assistant and a different audience/purpose; task facts and appropriateness do not worsen; and the person voluntarily uses it again after setup. If quality ties Markdown but setup/recurring effort falls, that supports a convenience subscription. It does not support a superior-voice-engine claim. Honcho would need a separately authorized, equal-input evaluation before asserting Milton beats it.

A possible plain-language mechanism sentence for later consideration: “Choose writing that sounds like you. Milton gives those exact examples to your connected AI for the next message.” It explains present behavior without claiming unique technology, automatic fine-tuning or measured results.

**Proposed pilot: six real tasks, two assistants, three conditions.** This experiment, its 36-draft size and its 20% threshold remain proposals; person consent and effort need to be settled before running it. Propose one consenting person, six short upcoming tasks spanning email, DM and Slack, including at least two distinct audiences/purposes. Use a frozen set of four to eight already approved, placeholder-safe examples and any approved rules; no bulk collection or new standing-rule inference. Keep held-out task facts separate from the example set.

Generate each task in both assistants, each in a fresh conversation under three conditions: A, task facts only; B, the same approved material supplied as a fixed Markdown attachment/paste; C, current Milton cover/report reads with the real intent. That is **36 short first drafts**, not a new evaluation platform. Hold model/settings and task prompts constant within each assistant. Do not fine-tune, rerank, add embeddings or change Milton during the run. Record whether the read succeeded and which samples C returned; do not silently exclude missed reads.

Before seeing the source condition, the person edits anonymized drafts to a version they would send. Randomize and counterbalance order across short sessions to reduce rehearsal effects; repeated tasks remain a limitation. Record active editing time, proportion accepted unchanged, normalized text change and whether each material edit fixes style, facts or task intent. Ask for a blind voice preference, but make actual editing the primary measure. Charge connection/approval/setup time to the overall effort, rather than hiding it outside the result. Perform this locally with approved material; no Honcho upload is part of the proposal.

Set a pilot decision rule before generating: advance only if C lowers median active editing time by at least 20% versus B, without more factual/task errors, with a positive direction in both assistants. The 20% is a proposed practical threshold, not a statistical claim or an existing goal. With six tasks, report every paired outcome and misses; this can falsify the pitch or justify a larger test, not establish a population effect. A→B estimates examples’ benefit; B→C estimates Milton’s additional service benefit. If C ties B, measure whether recurring effort still makes the service worthwhile. Investigate demonstrated failures before changing architecture.

**Evidence limits.** The review inspected public Honcho pages/docs, selected public repository files and the benchmark inventory; Milton public homepage/pricing/setup/privacy/notes HTTP responses; and Milton source/doc contracts. Public Milton reads returned 200. No authenticated account, private writing, credential, installation or third-party execution was used.

Not checked: Honcho billing/activation, actual injection, correction cleanup, scope enforcement, managed tool version, protected dashboard or drafting results; Milton authenticated save/download, future read adherence or real editing outcomes. Honcho tests and benchmarks were not run. Technical contracts and successful reads are not proof of better writing. The proposed experiment requires consent and does not authorize storing new writing or changing product behavior.
