# Focused Honcho source teardown

Reviewed **2026-11-05**, pinned to [`b57a3730d00a95efbcd1b203c130c47a6028c289`](https://github.com/plastic-labs/honcho/tree/b57a3730d00a95efbcd1b203c130c47a6028c289). This extends the [product comparison](honcho-2026.md). The [source manifest](honcho-source-manifest-2026.json) records the reviewed public commit and Git blob hashes for 51 collected files; the source snapshots are not vendored here. Findings concern the specific sections and paths cited below, not an exhaustive audit. All recommendations remain proposals.

**Verdict.** The source review was worthwhile. The most useful lessons are reliable context delivery, explicit handling of stale/empty/failed reads, and separating retrieval evidence from answer quality. I found no source-based reason to add embeddings, a reasoning layer or autonomous learning to Milton. Honcho’s implementation also exposes the cost of derived memory: a correction can involve independent conclusions, profile cards, history and client caches. Milton’s simpler approved-source model avoids much of that maintenance, although it cannot remove stale text already in an assistant’s context.

The strongest new finding is that integration behavior varies substantially. Cursor’s hooks inject at session start; Hermes has asynchronous per-turn recall and an optional stricter current-query path. “Automatic memory” does not identify one uniform guarantee. A second finding is that schema/prompt promises need checking against the code that persists results: I found a concrete source-cardinality mismatch in induction validation.

| Review question                                        | Source finding                                                                                                                | Lesson for Milton                                                                                                       |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Does relevant context actually arrive before drafting? | Different clients use different hooks, deadlines, caches and fallbacks.                                                       | Observe the client’s actual read and returned examples before attributing a writing result to Milton.                   |
| Does a correction remove the old influence?            | Create, delete, card update and cache refresh are separate operations.                                                        | Preserve explicit replacements, version fencing and on-read assembly; avoid derived copies without a demonstrated need. |
| Can the system show why it answered?                   | Evidence records retrieved conclusions/message references; it does not prove reliance or semantic correctness.                | Use existing sample IDs and match signals to diagnose delivery; assess writing through edits.                           |
| Do tests establish the promised outcome?               | There are meaningful integration and model-backed memory tests, but the inspected paths do not measure writing as the person. | Borrow the separation of retrieval checks from outcome checks, not the entire evaluation framework.                     |

**1. Context delivery: useful engineering, with concrete tradeoffs.**

Cursor’s `sessionStart()` fetches the person’s context and the project’s summary, emits additional model context and a status message, and explains that capture is enabled. Its `beforeSubmitPrompt()` records the new prompt but explicitly cannot inject context through that hook. Mid-session recall therefore depends on MCP use; it is not a new automatic style briefing before each prompt. [Session start](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/integrations/cursor/src/session-start.ts#L1-L54), [prompt hook](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/integrations/cursor/src/before-submit-prompt.ts#L1-L28).

The Cursor code provides practical integration details: stable session naming from repository origin, configuration shared across integrations, explicit user/assistant attribution and retry after ensuring peers. It also records prompts and responses automatically, with redaction and length limits. This is designed for conversation memory; it is not an exact approved-writing retention contract. Copying the capture loop would change Milton’s product boundary. [Shared hook code](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/integrations/cursor/src/common.ts#L60-L170), [response capture](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/integrations/cursor/src/after-agent-response.ts#L1-L24).

Two limitations matter. Its four-second wrapper surrounds selected recall operations, but peer/session factory calls occur outside those wrappers; it is not a proven four-second total startup bound. Also, failed/timed-out reads become `undefined`; if all retrieved sections are absent, the emitted text describes the account as having nothing recorded. Static inspection therefore identifies a path that can confuse unavailability with an empty account. I did not reproduce it against Cursor or the hosted service. Milton should preserve its distinction between failed reads and an actually empty report. [Timeout helper](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/integrations/cursor/src/common.ts#L125-L140), [startup assembly](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/integrations/cursor/src/session-start.ts#L20-L53).

Hermes is more sophisticated. It keeps static usage guidance separate from dynamic context, has independent cadence for basic context and synthesized recall, bounds initial waiting, reuses background work and backs off when recall stays empty. Later turns may consume work initiated by an earlier turn. These choices keep memory from blocking the conversation, but create a freshness tradeoff. [Prefetch path](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/hermes-plugin-honcho/__init__.py#L462-L616), [refresh cadence](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/hermes-plugin-honcho/__init__.py#L732-L766), [background result ownership and expiry](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/hermes-plugin-honcho/dialectic.py#L35-L117).

The default asynchronous supplement also builds a general person/session question unless optional query rewriting supplies another prompt. The incoming request influences heuristics, but its text is not automatically embedded in that default supplement’s question. The optional synchronous path explicitly includes the current request and bypasses earlier recall caches. Thus “prompt-related context” and “an answer computed for this precise request” are distinct mechanisms in the code. [Asynchronous prompt construction](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/hermes-plugin-honcho/dialectic.py#L141-L204), [current-query recall](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/hermes-plugin-honcho/recall_sync.py#L40-L95).

The strongest reusable pattern is in that optional path: one deadline, one active worker, captured session/turn identity and an operation-generation token. A timed-out or superseded worker cannot publish into the next request’s result. It is opt-in, not the default. Its tests explicitly switch topics, block a worker, advance/reset turns and switch sessions. [Implementation](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/hermes-plugin-honcho/recall_sync.py#L15-L119), [tests](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/hermes-plugin-honcho/tests/test_recall_sync.py#L48-L131).

Another tradeoff is deliberate retention of the last nonempty cached base context when a fresh result formats empty. That protects continuity after transient failures but provides no freshness proof after a person removes guidance. I found no version-fenced invalidation in this reviewed adoption path. This is a client-cache observation, not proof that all Honcho clients reuse deleted preferences. [Cache adoption](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/hermes-plugin-honcho/__init__.py#L510-L552).

**Milton implication:** do not build hooks because Honcho has them. First establish whether missed reads cause failed drafts in an actual client. If a hook is later justified, the small transferable requirement is that a result belongs to a particular request/account/version and an unavailable read must not be called empty. Milton currently has no need for Honcho’s multi-pass recall state machine.

**2. Corrections: original input, derived conclusions, profile and cache can disagree.**

The ingestion worker asks a model for explicit atomic observations and converts that output into stored representations. Source-message indices preserve links to the input; this is model-written extracted knowledge, not verbatim prose selected as an exemplar. [Deriver prompt](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/deriver/prompts.py#L62-L110), [model call and conversion](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/deriver/deriver.py#L185-L243).

The deduction specialist is instructed to find changed facts, create an updated conclusion, delete the outdated observation and update stable profile information. Those are model-directed tool operations. The reviewed conclusion API exposes creation and deletion, not a single operation that replaces an exact preference together with every dependent artifact. Individual write handlers commit separately; a whole dream is not one atomic semantic correction. [Specialist instructions](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/dreamer/specialists.py#L881-L942), [conclusion API](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/routers/conclusions.py#L29-L57), [write/delete handlers](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/utils/agent_tools.py#L1390-L1431).

Deleting one conclusion sets its deletion timestamp and removes retained history copies of that conclusion. Query paths exclude deleted rows, including a database check after external vector retrieval. That is a useful separation: an external index is not the final authority on whether content still exists. However, this single-conclusion deletion path does not traverse and remove derived children or rewrite a profile card; those are other operations. Dependencies can still be traversed explicitly. [Deletion](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/crud/document.py#L1253-L1293), [retrieval filtering](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/crud/document.py#L480-L623), [child lookup](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/crud/document.py#L2113-L2171).

History records are attached to the actual database writes rather than reconstructed from what the model says it did. It retains created IDs/source links, removed text and card before/after values. User-requested deletion erases the relevant history copies as well. That is good provenance engineering; it still records what changed, not whether the revised belief is true. [History writes](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/crud/dream_history.py#L136-L217), [history erasure](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/crud/dream_history.py#L405-L447), [deletion test](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/tests/crud/test_dream_history.py#L346-L419).

Profiles add another state surface. The internal agent tool structurally validates and bounds entries, and intentionally preserves the old card when an update is empty or wholly rejected. Its underlying API can set a list directly. Consequently, even “clear the profile” has different semantics depending on the path. This is a control-surface distinction, not an assertion that deleting a whole account leaves its profile behind. [Agent card update](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/utils/agent_tools.py#L1488-L1620), [card persistence](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/crud/peer_card.py#L80-L147).

Two details make the limits concrete:

- When semantic deduplication is enabled, near-duplicate survivors are chosen using token-set richness, with incoming text winning a tie. That is a storage heuristic, not a test of which preference is current, approved or correctly scoped. It would be unsuitable as Milton’s sample-replacement policy. [Deduplication choice](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/crud/document.py#L1743-L1770).
- The induction tool’s JSON schema asks for at least two source IDs, but `ObservationInput` requires only a nonempty list for induction, and the grounding filter accepts one real source for induction. The grounding step can therefore pass onward just one source after removing an invalid ID from a two-source proposal. The executor passes inputs to those handlers without a separate general JSON-schema validation step. This is a source-confirmed validation mismatch, not a remotely exercised failure. [Tool schema](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/utils/agent_tools.py#L126-L166), [runtime schema](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/schemas/internal.py#L104-L140), [grounding minimum](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/utils/agent_tools.py#L769-L844), [dispatch](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/utils/agent_tools.py#L2511-L2532).

The positive lesson is that they resolve cited source IDs against real documents in the correct observer/observed scope before persisting derived knowledge. Invented IDs can be stripped and unsupported writes refused. That prevents fabricated provenance, while leaving the logical validity of an inference to the model. Milton already applies the analogous stronger foundation for its own job: exact anchors must resolve, approved bodies are preserved and saves are fenced by a version. [Source grounding](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/utils/agent_tools.py#L769-L844), [Milton save contract](../../server/src/store/compiled.ts).

**Milton implication:** keep one authoritative approved source and derive reports deterministically. A model-written preference profile, separate summary or autonomous deduplication policy would create new correction obligations. Current server transactions and fresh reads simplify those obligations; they do not guarantee an outside assistant discards an earlier read.

**3. Retrieval and evidence: practical resource controls, no writing-quality shortcut.**

The inexpensive representation path blends semantic matches, optionally frequently rederived observations and recent observations. It tracks selected document IDs and refills unused capacity when earlier slices underfill. That is ordinary bounded selection with explicit fill behavior. It is not evidence that any particular weighting improves writing. Milton already fills broader sample slots deterministically, so there is no new ranking feature justified here. [Representation selection](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/crud/representation.py#L330-L424), [Milton selection](../../server/src/store/reports.ts).

The live reasoning path prefetches explicit and derived conclusions separately, reuses a query embedding and then offers search tools for further exploration. The lower tier fetches fewer conclusions. Keeping source classes separate prevents a large body of derived knowledge from crowding out directly stated evidence. Session allowlists remove unsuitable tools and disallow global memory briefs; empty allowlists return no memory instead of widening access. [Prefetch](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/dialectic/core.py#L293-L397), [tool selection](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/dialectic/core.py#L172-L190), [empty-boundary handling](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/utils/agent_tools.py#L1064-L1091).

The resource controls are real code, not just instructions to be concise: bounded tool iterations, input-token checks and a final synthesis step when tool rounds run out. Optional budget reminders tell the model how much remains, while runtime bounds retain control. The outcome records whether a limit was hit. These are useful patterns for a reasoning service, but Milton does not run a reasoning agent and should not acquire one to use them. [Tool loop](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/llm/tool_loop.py#L448-L585), [limit exit](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/llm/tool_loop.py#L805-L949), [budget tests](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/tests/llm/test_tool_loop_budget.py#L113-L230).

Message search results normally truncate at whole-snippet boundaries and explicitly say how many were omitted. A single oversized snippet falls back to marked truncation. This is a useful presentation lesson: omitted context must be legible. For Milton, whole approved examples or separately approved excerpts should remain the unit; do not silently cut a sample merely to fit an arbitrary context target. [Snippet assembly](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/utils/agent_tools.py#L2198-L2262), [tests](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/tests/utils/test_agent_tools.py#L1341-L1441).

The evidence accumulator is deterministic and optional. It deduplicates by record ID, records conclusion text and source links, and records raw-message references rather than copying unbounded message bodies. Prefetched conclusions are recorded after successful formatting; a test forces formatting failure and checks that the dropped block is not claimed as delivered. [Accumulator](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/utils/evidence.py#L110-L170), [prefetch recording](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/dialectic/core.py#L380-L397), [failure test](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/tests/dialectic/test_evidence.py#L228-L251).

It is still an exposure record, not a causal explanation or a complete prompt transcript. Profiles do not have conclusion/message identities, initial session history is injected through a separate path, and later context limits can remove material. A record being retrieved does not establish that the final model saw every byte or used it correctly. The code makes this limitation more concrete than the product page alone. [History injection](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/dialectic/core.py#L258-L291), [evidence classification](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/tests/utils/test_agent_tools.py#L2744-L2810), [loop truncation](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/src/llm/tool_loop.py#L554-L569).

**Milton implication:** the existing returned sample IDs, match signals and account version are enough for the next evaluation. Record the read outcome and selected examples in a private, consented experiment; then measure what the person edits. Do not add a permanent content log or claim sample exposure proves imitation.

The unified runner usefully separates retrieval-evidence assertions from synthesized-answer assertions. A system can retrieve the right material and still answer badly; those should fail different checks. It also waits for actual queue completion, rather than relying solely on a fixed sleep. The judge is another model, not the person whose writing is being evaluated. [Runner assertions](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/tests/unified/runner.py#L864-L939), [queue wait](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/tests/unified/runner.py#L713-L725), [test format](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/tests/unified/README.md#L68-L98).

I inspected CI configuration, not CI results. The model-backed unified suite is configured for relevant main pushes and selected PR-label runs; live provider tests are separately opt-in. Test existence is not a passing run, and a passing model-provider contract would not prove the writing outcome. [Unified workflow](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/.github/workflows/unified-tests.yml#L1-L65), [live-provider test documentation](https://github.com/plastic-labs/honcho/blob/b57a3730d00a95efbcd1b203c130c47a6028c289/tests/live_llm/README.md#L1-L13).

For Milton, borrow the distinction in the next small writing experiment, not the large framework: **did the right approved material arrive, and did the draft require fewer edits?** Keep tests focused on observed failures. This review does not justify growing the repository’s suite or building an LLM judge service.

**Decisions I recommend.** These are proposals; no implementation was performed.

| Decision                            | Concrete action                                                                                                          | Gate                                                                                                           |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| Adopt now as an evaluation practice | Capture successful/failed/empty read, account version and selected sample IDs separately from the person’s edit outcome. | The already-proposed consented first-draft experiment; no production content logging.                          |
| Preserve now                        | Exact approved sources, atomic saves, explicit retirement/replacement and deterministic report assembly.                 | Existing contracts; no new derived voice profile.                                                              |
| Investigate only after evidence     | A client-specific reminder or hook if missed reads materially hurt drafts.                                               | Observe the failure first; require bounded waiting, distinct error/empty status and request/version ownership. |
| Defer                               | Payload reduction or changed sample selection.                                                                           | Real writing demonstrates context pressure or wrong examples; then test one change.                            |
| Avoid for this goal                 | Autonomous profile inference, dreaming, semantic sample deduplication and another model over stored writing.             | No present justification; violates the settled processing/approval boundary where applicable.                  |

The review strengthens the case for Milton’s narrow architecture, not a moat claim. Honcho solves a larger continuity problem and carries the resulting correction and freshness machinery. Milton should prove the value of approved examples delivered for a specific writing job. Its remaining weak point is still the external assistant’s actual behavior and the person’s editing burden.

**Method and evidence limits.** This was static source research. Public GitHub files were read at one commit, mapped with ast-grep and inspected without importing or executing Honcho. All 51 collected snapshots matched their pinned Git blob hashes; 58 pinned source references and their line ranges were checked. The manifest makes the source identity reproducible without publishing copied third-party code.

Honcho tests were read, not run; no runtime/test pass is claimed. No dependencies were installed for the review, no private account or writing was accessed, and no live injection, correction propagation, managed deployment version or editing improvement was observed. Read correctness, retrieval exposure and fewer edits are separate outcomes. Any writing experiment or implementation remains separately scoped.
