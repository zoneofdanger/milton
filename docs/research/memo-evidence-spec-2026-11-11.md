# Spec: better evidence in a memo

Status: draft for Peter's approval, 2026-11-11. Spec only: no code, docs, migrations or
model calls were made. Written from milton-overlord's brief (internal working notes, not published).
Every statement about Milton today cites the code or doc it comes from. Where those
disagree with the brief, the next section says so.

---

## Summary (one page)

Today a memo is the AI's first draft, the accepted final, and up to 10 one-line tweaks
the AI writes ("vendor replies: no warm-up opener"). Milton has no means of checking a
tweak against the two texts, and it does not keep the person's request at all
(`docs/memos.md`, "What a memo holds").

This spec makes four changes, all model-free, through **one** new shape for
`create_memo`'s `memo`:

1. **Each tweak is tied to a before-and-after quote that code has checked.** The tweak
   line stays as the label. The quotes must come from places where the first draft and
   the final really differ, so a tweak can't be invented. Reports show each served tweak
   with one short example: `"Hi Dana, I hope you're well." → "Dana —"`.
2. **Code works out what changed; the AI only labels it.** At save, Milton compares the
   first draft with the final word by word and stores each changed spot. The AI quotes the
   spots it knows about and labels each one: **voice** or **content**, and typed by the
   **person**, **asked** for, or changed **unasked**. Code enforces the rule that a
   tweak sits only on a voice change the person typed or asked for. Unlabelled spots are
   still stored. Together the labels show which words in a final the person typed, so a
   future profile can learn from the person's words instead of the AI's.
3. **A tweak score from data already kept.** Milton already records which tweaks each
   report served (`memos.served_tweak_ids`) and which tweaks each memo taught
   (`tweak_citations`). A tweak that was served and then taught again by the same memo
   was **needed again**: it didn't work as written. The TPS page shows "served 5 · needed
   again 2"; reports mark tweaks that were needed again and give those tweaks' examples
   first. Nothing new is collected.
4. **The person's typed request, trimmed.** A new `request` field holds what the person
   typed to ask for the writing, at most 600 characters, with no pasted threads or quoted
   text. It is shown only to the person and **never served to AIs** in this change.

**For the person:** each memo page gets a "What changed" list (before → after, how it was
labelled, and which tweak it taught) and the request they typed, with a Remove button.
Each tweak on the TPS page shows its newest example and "served · needed again". The
receipt line doesn't change. "Tweak" stays the person's word.

**For their AI:** the `tweaks` list goes away. Tweaks now go on items in a new `changes`
list, and there is an optional `request`. The instructions' Tweaks paragraph is rewritten
at nearly the same length (441 to 455 characters). The details go in the input field
descriptions, which the served-budget test doesn't measure. A quote that doesn't match is
refused with a next step: copy it exactly, or leave that change out.

**In what Milton stores:** one new table (`memo_changes`), two new columns on `memos`
(`request`, `changes_state`), one on `tweaks` (`text_changed_at`). Everything is
additive, needs one Drizzle migration and one owner grant file, and touches nothing in
`neon_auth`.

**Build order:** the score first (read-only, no migration, gives a baseline), then one
release carrying changes 1, 2 and 4 together.

**What Peter decides** (end of this file): serving first-draft quotes to AIs, which
changes a privacy-page promise; refusing versus dropping a quote that doesn't match; no
tweaks on memos without a kept first draft; keeping the request on by default; and
approving about $3 for an offline test.

## Where the code and docs disagree with the brief

1. **Item 1 is a privacy step too, not only item 4.** The privacy page says "First drafts
   are shown only to you" (`apps/site/src/pages/privacy.astro`, "Who can see your memos").
   The terms say AIs read "your memos' finals and tweaks" (`terms.astro`). A served
   "before" quote is first-draft text, so both pages must change if quotes are served.
2. **"Needed again" depends on the AI reusing ids.** A memo cites a tweak only when the
   AI sends its `tweak_id` or the exact same normalized wording (`save.ts`,
   `normalizeTweak`). TODO #34 records that on #76's first instructions no AI reused an
   id (0 of 118 tweaks). After a rewrite of the Tweaks text, Claude reused the id in the
   one repeat qa reran. So the score's "needed again" count is a lower bound.
3. **Item 3 needs one small piece of metadata.** "Didn't work as written" requires
   restarting a tweak's count when the person rewords it, and the TPS page rewords in
   place, keeping the id (`tps.ts`, `rewordTweak`). That needs `tweaks.text_changed_at`.
   It records when, not anything the person wrote.
4. **Guidance has a fourth home.** The brief lists instructions, the tool description and
   error next steps. `docs/mcp.md` ("Served text") also lists the input field
   descriptions. `server/test/served-budget.test.ts` measures only tool descriptions, so
   field descriptions are where the detail fits.
5. **Today a memo with `first_draft_missing` may carry tweaks.** The only shape rule is
   that tweaks are refused when the final equals a kept first draft (`save.ts`,
   `memoShapeProblem`). Requiring evidence would end tweaks on missing-draft memos. This
   is decision 3.
6. **The brief's two labels need a third and a fourth value.** Redrafts often change
   words nobody asked about. Those spots are the AI's own voice getting into the final,
   which is the drift the brief wants to guard against. So `by` gets `unasked`, and code
   labels Markdown-only spots `format` by itself.
7. **No compatibility shim.** `docs/agents/working.md` rules out backwards-compatibility
   shims before launch, so the old `tweaks` field is refused with guidance rather than
   accepted.
8. **"Exact edits" is a retired phrase.** The copy-drift test fails on it in site and app
   copy (`docs/checks.md`). Exact edits were a different, removed feature: anchored
   replacements to stored bodies. The new quotes must never be called that.
9. **Save receipts outlive forgetting.** `save_requests` rows stay until account deletion
   (privacy page; `docs/saves.md`). So a save's stored outcome must never hold a request
   or quote text, only counts and tweak lines, as it does today.

## The new `memo` shape (the one change to `create_memo`)

Unchanged: `final`, `first_draft` or `first_draft_missing`, `mode`, `rounds`, `context`,
`kind_id` or `new_kind`, `report_id`; the request hash, replay, the account lock,
savepoint and receipt (`docs/saves.md`); `cover_sheet`, `forget_memos` and
`memo_context`.

Removed: `memo.tweaks`.

Added:

| Field              | Type and limit                                                                                          | Allowed when                                             |
| ------------------ | ------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| `request`          | string, 1–600 characters, at most 12 lines, trimmed, well formed, no control characters but line breaks | with `first_draft` or `first_draft_missing`              |
| `changes`          | array of 1–20 items; an empty list counts as omitted, before hashing                                    | with a kept `first_draft` that differs from `final`      |
| `changes[].before` | string, 0–300 characters: words quoted from the first draft                                             | `before` and `after` can't both be empty                 |
| `changes[].after`  | string, 0–300 characters: words quoted from the final                                                   |                                                          |
| `changes[].about`  | `voice` or `content`                                                                                    | required                                                 |
| `changes[].by`     | `person` (they typed these words), `asked` (they asked, you wrote them) or `unasked`                    | required                                                 |
| `changes[].tweak`  | `{tweak_id}` or `{text}` (one line, at most 200 characters), as today's tweaks                          | only with `about: voice` and `by` of `person` or `asked` |

Why these limits:

- **20 changes.** That is twice today's 10 tweaks, enough for a reworked email, while a
  long document's many small edits stay mostly unlabelled rather than costing the AI a
  long list.
- **300 characters a quote.** A quote locates a change; it isn't a copy of it. Anything
  longer is a rewrite, and code stores the real span anyway.
- **600 characters for `request`.** The own-words test's typed requests ran one to three
  lines, the longest about 480 characters. At 600 a whole ask fits, and a pasted email
  thread doesn't.
- **12 lines.** A typed ask is a few lines; a paste is many.

**What a tweak is after this.** A tweak is one line naming a voice habit the person
typed or asked for, with when it applies, shown with what it changed. Every new citation
points at a change code has verified. "Tweak" stays the person's word. It still fits,
and the receipt, TPS page and site already use it. `changes` is the field the AI sees;
on the page each item is a "change", in a list headed "What changed". One collision
to accept: a saved result already has a numeric `change` (the change score). The
field-description wording keeps them apart ("changes: the spots that differ").

**The result.** `memo` in a saved or unchanged result gains `changes: {found, labelled}`,
both counts. The receipt line is unchanged ("Kept memo: vendor decline, 2 rounds, tweaks:
no warm-up opener."). The stored outcome holds no quote or request text (point 9 above).

**Refusals.** All of them are found before any database work, because they depend only
on the input. They write no receipt, like today's shape refusals (`docs/saves.md`).

| Code                   | When                                                                                                                                                 | `next`                                                                                                                                                                                                                                         |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `invalid_input`        | `changes` without a kept first draft, or on a final equal to it; a tweak on a content or unasked change; empty quotes; limits                        | as today (`fix_input`), with a message naming the change by number                                                                                                                                                                             |
| `invalid_input`        | `request` on a final-only memo; over 600 characters or 12 lines; holds a line starting `>`, an "On … wrote:" line, or a `From:`/`Subject:` header    | `fix_input`: "Send only what the person typed to ask, without pasted or quoted text, or leave request out; save with a new request_id."                                                                                                        |
| `invalid_input`        | the memo carries `tweaks` (an AI holding the old tool definition)                                                                                    | `fix_input`: "tweaks now go on changes: quote before and after and add tweak there, or save without tweaks; new request_id." The result also announces `tools/list_changed`, as a stale `get_report` does today (`mcp.ts`, `staleReportCall`). |
| `invalid_change` (new) | a quote isn't in its text; it is, but not where the texts differ; it matches more than one changed spot; two changes label the same spot differently | `fix_input`: "Copy before from the first draft and after from the final exactly, add a few words if it appears twice, or leave that change out; save with a new request_id."                                                                   |

`invalid_change` joins `loggedErrorCodes` and `nextSteps` in `mcp-outcomes.ts`; its test
already requires every code to have a next step.

Decision 2 is whether `invalid_change` should refuse the save or drop the quote and save.
The recommendation is to refuse. The AI still has both texts in context when it saves,
and the next step always offers "leave that change out", so the memo is never lost
unless the AI gives up.

## 1. A tweak carries a checked before-and-after

**Contract.** Above: a tweak exists only on a `changes` item. Its quotes are checked
against code's own list of changed spots (section 2), so each citation points at a real
difference between the two texts.

**What is stored.** One `memo_changes` row per changed spot (section 2). A tweak's
evidence is the rows that name it. Each row stores code's own span text, not the AI's
quote: `before` and `after` as cut from the first draft and the final, each capped at 300
characters with a `truncated` flag. So what is shown and served is always verbatim text
from the stored memo.

**When code works.** At save it finds the spots and checks the quotes. At read it picks
one example per served tweak: among the rows naming that tweak, labelled voice, with
both sides at most 160 characters, it takes the newest from the intent's medium, else
the newest overall.

**How it is served.** Under each tweak in `# Your tweaks`, one line:

```
- vendor replies: no warm-up opener (4 memos; needed again 2 of 3)
  "I hope this finds you well! Thanks so much for reaching out." → "Thanks, but no."
- sign off –P (6 memos)
  added: "–P"
```

An insertion prints as `added: "…"` and a deletion as `cut: "…"`. Examples fill
in served order within a **3 KiB** budget. The first pass covers tweaks with "needed
again" of at least 1, the second covers the rest (section 3). A tweak with no example
that fits is printed as today. The 3 KiB keeps the report within about 10% of today's:
up to 32 KiB of examples, at most 1,500 characters of cover sheet, ten tweak lines
(`memos.ts`). Ten examples at 160 characters a side need at most about 3.5 KB.

Content changes are never served, only shown to the person. They may hold facts the
person removed. And the lint-then-revise test found that pushing an AI to cut costs
facts (`revise-results.md`: "$200 up front" was lost).

`get_report`'s `tweaks` envelope is unchanged (`{tweak_id, text, memos}`); the
examples go in the report text only. The `# Your tweaks` intro line gains one sentence:
`"was → now" shows a change the person made; "needed again" counts drafts that were given
the tweak and still needed it.`

**TPS page.** On the memo page, each change that taught a tweak shows the tweak beside
it. In the tweak list, each tweak shows its newest example under the line. Each memo row
keeps its "Served" and "Taught" lists (`memo-pages.tsx`).

**TPS.md.** Under `## Tweaks`, each tweak line is followed by its newest example, in the
same form as the report. First drafts stay out of the export (`docs/tps-page.md`); this
adds only the short quotes the tweaks rest on.

**Memos saved before.** They have no rows. Their tweaks and citations stay, and are
served without an example. No backfill (decision 9).

**AIs with the old definition.** See the refusal table. The first call after a release
already carries `notifications/tools/list_changed` (`docs/mcp.md`), so most clients
refresh before they save.

## 2. Code finds what changed; the AI labels it

**What code computes, at save, once.** When a kept first draft differs from the final:

1. Tokenize both texts as the change score does: words and single punctuation marks
   (`score.ts`, `tokens`), keeping each token's position. Case counts: "Hi" against "hi"
   is a change, because lowercase is a habit.
2. Strip the shared prefix and suffix, then run a Myers diff on the middle. It works
   within the change score's bound (`MAX_SCORED_CELLS`, 20 million) and gives up past it.
3. Merge edits separated by at most 2 unchanged tokens on the same line into one changed
   spot, so `Hi Dana,` → `Dana —` is one spot, not two.
4. A spot whose two sides hold only Markdown marks (`* _ # \` > ~ |`) and whitespace gets
`about: format` from code. Matching skips it, and coverage doesn't count it. This
   handles an AI that sends Markdown source as the first draft and a rendered copy as the
   final.
5. Store up to 100 spots as `memo_changes` rows. Each has its offsets in both texts (JS
   string indices, UTF-16 code units) and capped text. `memos.changes_state` becomes
   `itemized`. With more than 100 spots, or over the cell bound, it becomes `too_large`
   and no code rows are stored.

**Matching the AI's quotes.** To match, both texts and the quote are folded: NFC, curly
quotes to straight, every run of whitespace to one space. The fold only locates; stored
text is never folded. Dashes are not folded, because "no em dashes" is a habit.

- `itemized`: a quote must occur in its text, and the occurrence must overlap a changed
  spot on that side. An empty side, a pure insertion or deletion, is matched by the other
  side alone. When both sides are sent, they must land on the same spot or on spots the
  quotes jointly cover. A quote covering several spots labels all of them. When a quote
  occurs more than once, the occurrence that overlaps a spot wins. If more than one does,
  the quote is ambiguous (`invalid_change`).
- `too_large`: each quote must occur exactly once in its text and the two sides must
  differ. The change is stored as a row at those offsets, located by the quote rather
  than by code.
- Spots no quote covers stay as rows with no labels.

**The labels and what they protect.**

- `about`: `voice` (how it sounds) or `content` (what it says: a fact, a point added or
  cut).
- `by`: `person` when the person typed those words, either by pasting back an edited
  version or by giving the wording in a message. `asked` when they asked and the AI wrote
  the words. `unasked` when the AI changed it while redrafting.
- Enforced in code and in the schema: a tweak only on `voice` with `person` or `asked`.
  That turns today's guidance ("skip one-off facts they added and changes you made
  unasked", `mcp.ts`) into a rule the server checks.
- **Typed share** of a final: the share of its tokens inside `person` rows. It is
  computed at read and shown on the memo page ("you typed 18% of this final"). This is
  the "who typed what" signal. It is not used for ranking or tiers in this change. It
  lets any later profile (the voice linter, TODO #36's pooled deletions) count only words
  the person typed plus "your words" finals. The stylometry note's trap list names
  "learning the AI's own voice from AI-assisted finals" (Malik & Awan 2026), and this is
  the guard against it.

**TPS page.** The memo page gets "What changed". Each spot shows before → after, a
"how it sounds" or "what it says" tag, "you typed / you asked / AI changed it unasked"
(or "not labelled"), its tweak, and the typed share at the top. A `too_large` memo says
"Too different to list every change; showing the ones your AI named." Highlighting the
spots inside the two full texts is optional; the Designer decides. Each memo row in the
list adds "N changes" to the line that already shows rounds and change.

**TPS.md.** Not exported per memo; the export has no first drafts, and a full memos
download remains a separate item (frozen spec, "Phase 1b").

**Memos saved before.** `changes_state` is null, read as "saved before changes were
listed". Code could compute their spots, but there would be no labels; decision 9
recommends no backfill.

## 3. A tweak score from data Milton already has

**Definition.** For a tweak _t_, count the memos that:

- have a kept first draft, because only those can cite tweaks under decision 3, so a
  missing-draft memo would look like a success it isn't;
- name a `report_id` whose served tweaks include _t_ (`memos.served_tweak_ids`);
- were saved after _t_'s text was last set (`coalesce(text_changed_at, created_at)`).

Then:

- **served(t)** is that count;
- **needed again(t)** is how many of those memos also cite _t_ (`tweak_citations`).

A served tweak that wasn't needed again is _not_ counted as a success: the draft may not
have called for it. Only "needed again" is informative. No ratio or percentage is shown
under 5 servings. The stylometry note's rule of three says "0 of 5" bounds a rate only
at about 45%.

**Computed at read, never stored.** On the TPS page as one more aggregate in the page's
statement (`tps.ts`, `read`). In `get_report` from fields its first statement already
loads: every memo's citations. It also needs `served_tweak_ids`, `first_draft_state` and
`created_at` added to each candidate (`memos.ts`, `readReport`). Reads stay at two
statements.

**What it is used for:**

1. **The person:** the TPS tweak list shows "served 5 · needed again 2" (with
   "since reworded" when it applies). A tweak that keeps being needed is one to reword,
   or to put on the cover sheet in the person's own words. The person does that; the AI
   never moves tweaks onto the cover sheet (`mcp.ts`, "Cover sheet").
2. **The AI:** the report prints "needed again M of N" after a tweak's count when M is at
   least 1, and gives those tweaks' examples first in the 3 KiB budget. The
   lint-then-revise test found the AI fixed every concrete, evidenced non-length flag it
   was given (`revise-results.md`); this gives the tweaks that fail the most concrete
   evidence.
3. **Evaluation:** the account-wide rate of "needed again" per serving is the plainest
   model-free measure of whether served tweaks work (see "How we'll know").
4. **Not used to hide, demote or reorder tweaks.** A tweak needed again is still needed,
   so serving it less would be backwards. Tweak order stays as `selectTweaks` ranks it.

A second free measure comes from the same data: **needed but not served**, a tweak a
memo cites that existed before that memo's report but wasn't in it. That is a ranking
miss, not a wording miss. It is for evaluation only and not shown.

**Rewording.** `rewordTweak` sets `tweaks.text_changed_at`, so the counts restart for
the new wording. Deleting a tweak removes its counts with it.

**TPS.md.** Each tweak line gains its counts: `- no warm-up opener (4 memos; served 5,
needed again 2)`.

**Memos saved before** count fully: served tweaks and citations have been recorded since
#76. So this item works on day one and gives a baseline.

## 4. The person's typed request, trimmed

**Contract.** `request` is optional, on drafted memos only, limits as above. It holds the
person's own words asking for this writing: the instruction they typed to start it,
exactly as typed. It does not hold their later corrections, which stay out of memos as
today. The AI cuts pasted or quoted material (an email they're replying to, a thread, a
document) and anything secret, marking each cut `[…]`. It changes nothing else: no typo
fixes, no rewording, no placeholders for names. That keeps it usable for the own-words
measure, which counts phrases copied from what the person typed (`own-words-test/plan.md`).

In edit mode the request is the instruction ("tighten this, keep my sign-off"), never the
text they gave the AI to edit.

**Stored.** `memos.request`, nullable. It isn't added to the search vector or used in
ranking: changing a generated column means re-adding it, and the request's ranking value
is untested.

**Not served to AIs.** Not in reports or in `get_report`'s envelope. It is shown only to
the person, as first drafts are today. Serving past request → final pairs to the AI ("they
said this, and sent that") is the obvious next use, and the own-words test points that
way: it found the AI reused more of a person's phrasing when told to. That needs its own
decision and test after this ships (slice 4).

**TPS page.** The memo page shows "You asked:" with the request in full and a **Remove**
button. That is one POST with the existing CSRF and Origin checks, setting `request` to
null under the account lock. Memo rows show the first line, cut to 120 characters.

**TPS.md.** Each memo shows `Asked: …` under its summary line.

**Keep memos and forgetting.** With Keep memos off, drafted memos are refused
(`memos_off`), so no request is kept. Final-only memos take no request. Forgetting a memo
or Delete all memos removes it with the memo row.

**Memos saved before** have none.

## Served text: where the guidance goes

Measured on 2026-11-11 with the current code: read-write instructions are 3,222
characters, read-only 935. Tool descriptions: `get_cover_sheet` 507, `get_report` 763,
`create_memo` 1,741, against budgets of 570, 860 and 1,900 (total 3,300) in
`served-budget.test.ts`. The unapproved own-words sentence is 239 characters.

- **Instructions:** replace the Tweaks paragraph (441 characters) with this one (455,
  counted):

  > Changes: when the final differs from your first draft, send changes: before and
  > after quoted exactly, a few words each, with about (voice or content) and by (person,
  > asked or unasked). Tweak only a voice change, with when it applies ("vendor replies:
  > no warm-up opener"); reuse a served tweak's id. request: only what they typed to ask.
  > Never send secrets, pasted text, their corrections or other people's text; summarize
  > the situation in context.summary.

  The read-write total becomes **3,236**; with the own-words sentence, **3,477**, 23
  under the 3,500 cap. That fits, but nothing else will. If both ship, the next addition
  has to replace text. The read-only variant is unchanged.

- **`create_memo` description:** replace the tweaks sentence (208 characters) with one
  of about 250: "changes, only when the final differs from a kept first draft: what
  changed, before and after quoted exactly, with about and by; tweak ({tweak_id} or
  {text}) only on a voice change they typed or asked for. request: their own typed ask,
  no pasted text." That makes about 1,783, under 1,900.
- **`get_report` description:** add "each tweak with an example of what it changed"
  (about +45, to about 808, under 860).
- **Field descriptions** carry the detail and examples: the meaning of each `by` value,
  "a few words, copied exactly; for an insertion leave before empty", "never 'when
  requested'", and the request's cut rule with `[…]`. These are served in `tools/list`
  but not budgeted, so they are where growth belongs.
- **Error next steps:** `invalid_change` and the old-`tweaks` refusal, as in the table.
- **The setup script's** "(no first_draft, mode, rounds or tweaks)" becomes "… or
  changes" (`setup.ts`).
- **The site's For agents page** repeats the save rules (`for-agents.astro`, "Saving and
  export") and needs the same sentence.

## Schema and migrations

Following `docs/deploy/migrations.md`: snapshot first, rehearse on a throwaway branch or
disposable database (`check-auth-integration.ts`, PostgreSQL 18), one migrator, owner
URL only in the environment, then the role audit (`check-runtime-role.ts`). Nothing
drops, so no `code-stopped-by` line is needed. The migration is additive and backward
compatible: the running code never names the new columns, and inserts leave them null.
So traffic may stay open, per "Additive and incompatible changes". Nothing touches
`neon_auth`.

**Drizzle `0015_memo_evidence.sql`** (slice 2), with `SET LOCAL lock_timeout '5s'`:

- `memos.request text` with a check: null, or a drafted memo
  (`first_draft_state <> 'none'`), 1–600 characters, trimmed, no control characters but
  `\n`.
- `memos.changes_state text` with a check: null, or `itemized` / `too_large` and only
  when `first_draft_state = 'kept'`.
- `tweaks.text_changed_at timestamptz`.
- `memo_changes`:
  - Columns: `user_id`, `memo_id`, `n` smallint 0–99, `draft_start`, `draft_end`,
    `final_start`, `final_end` (int, ≥ 0, start ≤ end), `before`, `after` (text, at most
    300 characters each), `truncated` boolean, `about` (null, `voice`, `content` or
    `format`), `by` (null, `person`, `asked` or `unasked`), `tweak_id` (nullable).
  - Primary key: `(user_id, memo_id, n)`.
  - Foreign key `(user_id, memo_id)` → `memos`, on delete cascade.
  - Foreign key `(user_id, memo_id, tweak_id)` → `tweak_citations`' primary key, on
    delete set null (`tweak_id`). PostgreSQL 15 or later supports the column list. This
    means a change's tweak is always one its memo teaches, and deleting a tweak keeps the
    change while clearing its link.
  - Checks: a tweak only with `about = 'voice'` and `by` of `person` or `asked`;
    `format` rows have no `by`.
- Adding the checks scans `memos` once; the table is small.

**Owner file `016-memo-evidence-roles.sql`** (after 0015, before the code):

- MCP: `SELECT, INSERT` on `memo_changes`.
- App: `SELECT` on `memo_changes`, `UPDATE(request)` on `memos` (for Remove), and
  `UPDATE(text, norm, text_changed_at)` on `tweaks`.
- New `memos` columns need no grant for MCP inserts, because 014 grants table-wide
  `INSERT, SELECT`.
- It must restate 014's full set for the memo tables, revoking before granting. Otherwise
  rerunning 014 would silently drop the new column grants.
- Update the expected owner-file list and privilege lists in
  `server/scripts/auth-integration.ts`.

**`docs/deletion.md`:** forgetting a memo or Delete all memos removes its changes and its
request (cascade and the memo row). Deleting a tweak keeps the changes and clears their

**`docs/deletion-inventory.txt`:** add `changes_state request` to `public.memos`, and add

Cascades from memos and users; forgetting a memo or "Delete all memos" removes it first.`
`deletion-inventory.test.ts` fails without these.

**Keep memos.** No new switch is recommended (decision 5). Off already refuses every
drafted memo, so it stops changes and requests too.

**Keeping secrets and other people's details out:**

- **Request.**
  - The AI is told to send only the person's own typed instruction and to cut pasted
    text and secrets.
  - The 600-character and 12-line caps make a pasted thread impossible to fit.
  - Code refuses quoted lines (`>`), "On … wrote:" lines and mail headers.
  - The request is never served to an AI.
  - The person sees it on every memo and can remove it.
  - Honest limit: Milton can't recognize a secret or a private detail in general, just
    as with finals today ("Milton cannot check what an AI sends", privacy page). Names
    are kept as typed, consistent with finals.
- **Quotes.**
  - Every stored and served quote is code's cut from the two stored texts, so nothing
    reaches Milton that wasn't already in the memo.
  - Only voice changes are served, at most 160 characters a side. Content changes, which
    may hold the facts the person removed, are shown only to them.
- **Receipts** store counts and tweak lines only, never request or quote text, because
  receipts outlive forgetting.

## Edge cases

| Case                                            | What happens                                                                                                                                                                                                                          |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Final-only memo (setup, "remember this")        | No `changes`, no `request` (refused). Unchanged from today.                                                                                                                                                                           |
| `first_draft_missing`                           | `request` allowed; `changes` and tweaks refused (decision 3). The `request_too_large` next step (resave with `first_draft_missing`) therefore drops tweaks; the result says so.                                                       |
| Untouched final                                 | `changes_state = itemized` with no rows; `changes` refused as tweaks are today; `request` kept: a request whose final was accepted untouched is the clearest success record Milton has.                                               |
| Edit mode                                       | The diff runs from the AI's first edit to the final. The person's original text isn't kept today and still isn't. Reverts ("kept my sign-off") are `by: person`. The request excludes the text to edit.                               |
| Pure insertion / pure deletion                  | One side empty; matched by the other side; served as `added:` / `cut:`.                                                                                                                                                               |
| Very long texts                                 | Over the 20-million-cell bound or 100 spots: `too_large`, quotes checked by unique occurrence only. Finals over 128 KiB are already never served as examples (`memos.ts`).                                                            |
| A quote that appears twice                      | The occurrence overlapping a changed spot wins; more than one is `invalid_change` ("add a few words").                                                                                                                                |
| Whitespace and Markdown differences             | Whitespace runs fold when matching; Markdown-only spots become `format` from code and need no label.                                                                                                                                  |
| Curly versus straight quotes                    | Folded for matching only.                                                                                                                                                                                                             |
| Replay and request hash                         | `changes` and `request` are part of the hashed input (`save.ts`, `hash(input)`). An empty `changes` reads as omitted before hashing, as `tweaks` does today. The diff is deterministic, and replays return the stored outcome anyway. |
| The same memo saved again with different labels | Returns `unchanged` with the memo on file, as today (`save.ts`: same final, state and first draft). New labels are ignored, so nothing counts twice.                                                                                  |
| A tweak named on two changes of one memo        | One citation (as today); both rows point at it.                                                                                                                                                                                       |
| The person rewords a tweak                      | Its examples stay; its counts restart.                                                                                                                                                                                                |
| A client sends `changes` as a JSON string       | Refused by the schema. If qa sees it, extend the argument repair in `mcp.ts` (`parsedObjectArguments`).                                                                                                                               |

## How we'll know it's better

The positioning test is the bar: does it make the first draft sound more like the person,
with less effort (`docs/positioning.md`)? Only item 1 claims a draft effect. Items 2–4
collect evidence. No copy may claim Milton improves the more it's used; a retention test
found no gain past about 10 memos.

**E0, free (slice 0, before any product code).** Run the diff, merge, format and match
code over the fictional pairs already on disk: the 35 back-draft pairs, the 17
lint-then-revise before/after pairs, and the own-words arms. Measure spots per pair, the
`too_large` rate, format spots and run time. Set the merge gap and the 100-spot cap from
the results rather than these guesses. Count the served text. No model calls.

**E1, does a snippet beat a line? (offline, fictional, paid: needs Peter's approval).**

- **Memos.** The 35 back-draft pairs are the memos: the back-draft is the first draft,
  the person's own email is the final, 7 fictional people.
- **Labels.** One `chat-latest` call per pair writes the changes, labels and tweaks, as a
  saving AI would. That is 35 calls, about 1.5k input and 400 output tokens each, about
  $0.70. The builder could write them by hand instead, for free, at the cost of realism.
- **Drafting.** 3 held-out briefs per person from the voice-linter's 39, so 21 briefs,
  each drafted under three arms:
  - A: the report with tweak lines only;
  - B: tweak lines plus examples;
  - 0: no tweaks.
    The examples are the same in every arm. That is 63 calls at about 5k input and 250
    output tokens, about $2.05.
- **Cost.** About **$2.75** in total at the prices the own-words plan used ($5 and $30
  per million), with a hard cap of $4. A second model family would roughly double it.
- **Measures, model-free and set before running:**
  - linter flags on the features the tweaks target, reported apart from the other
    features, so we don't grade with what we steer (stylometry note, trap 1);
  - length against the person's range;
  - facts kept (keyword cues, confirmed by hand);
  - a **priming check**: how often each served "before" phrase appears in the drafts.
- **Bar:** B cuts tweak-targeted flags by at least 30% against A, loses no more than one
  fact across all drafts, raises other flags not at all, and doesn't increase "before"
  phrases. Peter blind-reads the 21 triples.
- **Limits.** The people are fictional caricatures. The pairs are simulated, not
  rejected drafts (`back-draft-results.md`, Limits).

**E2, capture on real clients (needs Peter's approval; model calls on Claude Code and
Codex subscriptions, no API spend).** 10 scripted conversations per client against a
local server with a fictional account. The scripts include typed edits, asked-for
changes, an unasked rewrite, a fact the person adds, and a request with a pasted email.
Measure:

- the save succeeding on the first try and after one fix;
- the `invalid_change` rate;
- `by` and `about` against the script;
- coverage (labelled spots ÷ non-format spots);
- whether the pasted email stayed out of `request`.

Bar: at least 95% of memos saved, at least 90% of labels right, 0 pasted text kept, and
an `invalid_change` rate under 5% of saves. Above 5%, switch decision 2 to "drop and
save".

**Once a real person's memos exist** (Peter's account; a report-only script needs his go

## Reasons not to

**1. Before-and-after on a tweak.**

- _Strongest:_ nothing shows a pair beats a line. And a served "before" puts the exact
  AI phrasing to avoid in front of the AI that will write the next draft. Negative
  examples can prime what they forbid. E1's priming check is there for this, and it may
  fail.
- _Friction:_ the AI must quote exactly. Quoting errors are a new way for a save to
  fail, and a failed save loses a memo if the AI gives up after the refusal.
- _Privacy:_ it breaks a promise on the privacy page ("first drafts are shown only to
  you").
- _Cost:_ about 3 KiB more per report, and 23 characters of instruction headroom left if
  the own-words line ships too.

**2. Code computes the changes; the AI labels.**

- _Strongest:_ most of the payoff, the typed share and clean profile input, goes to
  features nobody has approved: the linter, TODO #36, tier changes. Peter set memos up as
  "light by design". This adds a table and a matcher on the bet that those features
  come.
- _Accuracy:_ the labels are still the AI's judgement, and `by: person` is a guess
  whenever the person edits outside the chat. A token diff of a rewritten paragraph
  produces spots that read oddly.
- _Friction:_ each change now needs two labels, so listing changes takes the AI more
  work than listing tweaks did.

**3. The tweak score.**

- _Strongest:_ at one person's volume, most tweaks will be served 0–3 times for weeks,
  and "needed again" undercounts whenever the AI writes a new wording instead of reusing
  the id (0 of 118 reused, TODO #34). The numbers can mislead more than they inform. The
  TPS page has to show raw counts, not rates, for that reason.
- _Over-application:_ "needed again" in a report may push an AI to apply a tweak where it
  doesn't belong, including in edit mode, where guidance must never widen scope.

**4. The typed request.**

- _Strongest:_ it keeps data with no draft benefit until a later decision serves it. And
  it is the most private text in the conversation: names, money, family events, as the
  own-words gists show ("my sister's graduation", "$200 up front"). Its trimming relies
  on the AI, which Milton can't check.
- _Friction:_ one more field the AI must compose correctly, and one more way for a save
  to be refused.
- _Trust:_ people type to their AI, not to Milton. Keeping it by default could surprise
  them, so the privacy page must say it plainly.

## Follow-up notes (after approval)

Added on 2026-11-11, after the offline test; the text above is unchanged.

- **The offline test (E1)** ran on `chat-latest` and spent $2.63 of its $4 cap. Under
  the one-label-per-spot rule above, 30 of 35 first saves were refused ("two changes
  label the same spot differently"): on a rewrite, one code spot holds several changes
  an AI names separately. milton-overlord therefore adopted **per-change rows**: one
  stored row per accepted change, cut from the stored texts at its quotes and still
  required to overlap a changed spot, plus an unlabelled row for each spot no change
  covers. Several changes may share a spot. It also adopted the **locating fold**:
  `*`, `_` and backticks dropped and em and en dashes read as hyphens, for locating
  only; stored text stays code's cut.
- **Tweak inflation.** E1's AI put a tweak on 147 of 150 changes. Peter approved,
  typing in milton-overlord's pane on 2026-11-11 ("Go with all four, how do we fix
  inflation?"), shipping the examples, a cap of three tweaks per memo, and "recurring
  habits only" guidance: a tweak is the exception, most memos teach one or none, and
  every change is recorded either way.
- **Plainer tweak wording.** Later that day Peter approved, typing in milton-overlord's
  pane ("go on the re-run and the wording"), served text that names a tweak's habit
  plainly ("no warm-up opener") and adds a condition only when the habit doesn't hold in
  all the person's writing, in place of "with when it applies".
- **The re-run.** The same 35 saves, run against slice 2's served text and save checks
  as built ($1.30 of a $2 cap): tweaks per memo fell from about 4.2 to 1.5 (26 new
  tweaks instead of 130), served tweak ids were reused 28 times instead of 7, the cap of
  three was never hit, 29 of 35 saved on the first try and 136 of 138 quotes matched.
- **Reuse before new, tested and set aside.** A save-time check that refuses a new
  tweak worded like an existing one, offering up to three candidates, was replayed on
  E1's tweaks (word overlap on the habit at 0.2 or more caught 46 of 54 hand-labelled
  repeats with no false alarm) and run in the re-run, where it refused 2 of 35 saves and
  the AI then picked correctly both times. With the cap and the wording, too few repeats
  were left to justify another refusal path, so milton-overlord set it aside.
- **A moved sentence.** The re-run found an AI correctly pairing a sentence the person
  moved and reworded, which code sees as a deletion at one spot and an insertion at
  another; requiring both quotes to share a spot refused it. Each quote must still
  overlap a changed spot on its own side, but the two sides may now sit at different
  spots, as "spots the quotes jointly cover" above allows.
- **Examples for every served tweak.** Decision 8's split needs a real account switched
  on, which was not cleared, so slice 2 serves examples for every served tweak.
